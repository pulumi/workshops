## Story

**1. The moment.** July 2025: Google's Gemini CLI coding agent was asked to rename a directory
and move its contents elsewhere. Its directory-creation call silently failed; the agent
proceeded as if it had succeeded anyway, cascading move commands into a target that did not
exist and scattering the user's files. Asked to explain, it wrote: "I have failed you
completely and catastrophically. My review of the commands confirms my gross incompetence."
Initial coverage described the files as destroyed. Days later, on the same GitHub thread, they
turned up sitting at the root of the C: drive: misplaced, not gone. The agent had been
confidently wrong in both directions — first about what it had done, then about what it
couldn't undo — and its own narrative was the only account anyone had of the outcome, right up
until someone went and looked.
(Source: GitHub issue google-gemini/gemini-cli#4586; WinBuzzer, "Google's Gemini CLI Deletes
User Files, Confesses 'Catastrophic' Failure," 2025-07-26; retrospective at
useheadlights.com/library/HD-INC-068/. Read 2026-09-30.)

**2. The tension.** The agent apologized instantly, and clearly meant it. Nobody could tell,
from that apology, what had actually happened to the files.

**3. Why it is hard.** A self-managed agent runtime (like the one in this workshop's AKS
sibling) puts you on the hook for the runtime, but you also own every log and every audit
trail. A Foundry-managed agent hands the runtime to Azure — but "managed" doesn't yet mean
the agent itself is an ARM resource: Microsoft's own quickstart for it has no Bicep, ARM, or
Terraform tab, only an SDK call. So the question this workshop actually answers isn't
"self-managed or managed" — it's "who is answerable for this agent's actions, and how do you
go check."

**4. The questions.**
- Q1: Who provisioned this, and can you prove it?
- Q2: What is the agent running as, and what can it actually touch?
- Q3: Where is the resource for the agent itself?
- Q4: What is it grounded in, and can you scope that down?
- Q5 (answered by the demo, not explained in advance): How do you verify what it actually did,
  and that it is really gone when you are done?

**5. The answers.**
- Q1 → Pulumi IaC generally: the whole platform is Python, in state, in git, reviewable with
  `pulumi preview` before anything runs.
- Q2 → `cognitiveservices.Account` (kind `AIServices`, `allow_project_management=True`) +
  `cognitiveservices.Project`: ordinary ARM resources, in the normal Azure resource graph,
  under normal Azure RBAC.
- Q3 → the agent itself has no ARM representation; `pulumi_command.local.Command` wraps the
  `azure-ai-projects` SDK call so it still gets a tracked create/delete lifecycle under
  `pulumi up` / `pulumi destroy`, instead of an untracked portal click.
- Q4 → a private, AAD-only blob container (no shared key) holding the org's own runbooks, wired
  in via a `cognitiveservices.ProjectConnection`, with a file-search tool scoped to only that
  container.
- Q5 → the demo: 05-exercise shows the agent citing an actual runbook filename back (grounding,
  not a generic chatbot answer); 06-teardown shows that `pulumi destroy` alone is not proof of
  a clean exit for this resource type, and the explicit soft-delete purge check is what actually
  closes the loop.

**6. The proof.** The demo runs 02→06 in order. 05-exercise proves grounding works: the agent
answers a real IT-ops question and names the runbook it used. 06-teardown proves the exit is
clean: reverse-order destroy, then a verification script that checks (and if needed purges)
Cognitive Services' soft-delete state. Q5 is the question the demo answers, last.

## Open questions for the PR

- Foundry per-agent pricing is not independently verified in the demo build; no cost figure
  appears on any slide or in speaker notes.
- The build workstation had no Azure tenant: `pulumi preview` ran clean on every folder and
  every program compiled, but no `pulumi up`, the live 05-exercise call, or 06's actual
  purge were executed. Speaker notes say so; no slide claims a live run happened during the
  build.
- Fact-check (2026-09-30): the Pulumi azure-native registry has since added a
  `cognitiveservices.AgentDeployment` resource that deploys a *reference* to an agent
  (`agent_id`/`agent_name`/`agent_version`), not the agent's own definition. It does not
  give you an ARM resource for the agent's prompt/instructions/tools -- those still only
  exist as the SDK-created data-plane object this deck describes -- so the deck's "no ARM
  resource behind it" claim holds. Worth a reviewer's second look before shipping, since
  it is exactly the kind of registry addition that could make this claim stale fast; recheck
  https://www.pulumi.com/registry/packages/azure-native/api-docs/cognitiveservices/ close to
  delivery.
- Fact-check (2026-09-30): could not independently confirm `FileSearchToolDefinition`'s
  connection-scoping behavior against a live, current (non-classic) Microsoft Foundry doc --
  searches surfaced only the deprecated "classic" file-search docs. The claim on the
  04-tool-connection slide is grounded in this run's own reading of `agent_with_tool.py`
  and that folder's AGENTS.md (which already flags the SDK shape as best-current-knowledge,
  unverified against a live tenant), not in independent Microsoft documentation. A reviewer
  with real Foundry/Azure AI Projects SDK access should confirm `FileSearchToolDefinition`'s
  fields before this ships.
