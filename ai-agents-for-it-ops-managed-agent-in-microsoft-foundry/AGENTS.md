## What this folder is

The material for the workshop "AI Agents for IT Ops: Managed Agent in
Microsoft Foundry" (scheduled 2026-12-09, plus one undated second regional
delivery; event page and speakers not yet assigned as of this run). This
run built the demo code only. Slides follow on this same branch in a later
run — see README.md's "Layout" section for the up-to-date state of both.

The repo carries what an attendee or a future presenter needs: the deck, the
demo code and these notes. The presenter's own working documents — the
brief, the rehearsal checklist, the fact-check log, open questions — stay
off this repo; `.gitignore` keeps every `*.md` out except `README.md`, the
`AGENTS.md` files and `slides/slides.md`. If you write a new working
document, it is ignored by default; that is deliberate, do not force-add
it.

## The central fact this workshop is built on

Azure AI Foundry has two layers, and only one of them is an ARM resource:

- The **project layer** (the account, the project, the model deployment) is
  now fully covered by `pulumi-azure-native` (`cognitiveservices.Account`
  with `allow_project_management=True`, `cognitiveservices.Project`,
  `cognitiveservices.Deployment`) as of provider `3.14.0`
  (`pulumi/pulumi-azure-native#4354`, closed/fixed, 2026-02-23). Do not use
  the classic `azure.aifoundry.Project`/`Hub` resources — the registry page
  itself now calls hub-based projects legacy and points at the
  `azure-native` resources used here.
- The **agent itself** (`02-foundry-platform`'s sibling, `03-agent`) is
  *not* an ARM resource on either provider. Microsoft's own quickstart
  creates it only through the `azure-ai-projects` SDK or a direct REST call
  to the project's data-plane host — no Bicep/ARM/Terraform tab exists on
  that page. This is a gap in what Azure exposes, not a gap in Pulumi's
  coverage. `03-agent` and `04-tool-connection` wrap the SDK call in a
  `pulumi_command.local.Command` (`create` + `delete`) so `pulumi up` /
  `pulumi destroy` still drive the agent's lifecycle honestly, instead of
  leaving it to a manual portal step that `destroy` can't clean up.

See each numbered folder's own `AGENTS.md` for the resource-shape
assumptions this run could not verify against a live tenant, and the
pull request description for the full research trail.

## Demo code

Six numbered folders, run in order; each folder's own `AGENTS.md` covers
its assumptions and what could and could not be verified from this build
workstation (no `az` CLI, no Azure tenant, no `azure-ai-projects` install
credentials — see README.md's "Run the demo" section for exactly what that
means for each step).

- `01-preflight/`: bash only, not a Pulumi project. `shellcheck` clean.
- `02-foundry-platform/`, `03-agent/`, `04-tool-connection/`: Pulumi Python
  projects (`runtime: python`, `pip` toolchain, per-folder `venv`). Each
  program must import and compile cleanly (`python -m compileall`) against
  its own `requirements.txt`, and `pulumi preview` must get at least as far
  as dispatching every resource constructor without a Python
  `TypeError` for an unexpected keyword argument — that is what a wrong
  property name raises immediately, before any network call, and it is the
  one check this build workstation could actually run without Azure
  credentials.
- `05-exercise/`: a plain Python script, no Pulumi project. Same
  compile-clean bar.
- `06-teardown/`: bash. `shellcheck` clean. Must include a Cognitive
  Services purge / `list-deleted` check — these accounts soft-delete, so
  `pulumi destroy` alone does not guarantee the account name is free for
  reuse.
